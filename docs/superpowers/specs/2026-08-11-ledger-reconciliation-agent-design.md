# 智能对账分析 Agent 设计

日期：2026-08-11

## 1. 目标

构建一个可独立运行的智能对账分析 Agent。用户可以选择或输入一个合成对账案件，Agent 自主查询案件、支付、账本和审计证据，检索适用的版本化对账规则，给出带引用的原因判断和处理建议。涉及案件解决时，工作流必须暂停并等待人工确认，确认后才更新 Agent 自己的数据；Agent 不提供修改余额、支付或账本的能力。

本项目是独立仓库、独立服务和独立数据库，不修改也不依赖 `ledger-reconciliation-platform` 的代码、数据库或运行环境。Java 账本平台只是领域背景，不属于本版本的构建或运行依赖。

## 2. 上游基础与原创边界

项目使用以下 MIT 许可的官方项目作为工程底座：

- `langchain-ai/agent-chat-ui`：Next.js 聊天界面、消息流式展示和 artifact 展示能力。
- `langchain-ai/react-agent`：LangGraph ReAct Agent 的最小 Python 模板。

仓库必须保留上游许可证和版权声明，并在 README 中说明来源。项目自行实现的内容包括：中文对账界面、合成业务数据、领域工具、版本化 RAG、证据检查、人工确认、执行记录、评测集、测试、容器化和文档。不得把上游 UI 或 Agent 框架描述为从零开发。

## 3. 范围

### 3.1 必须实现

- 中文聊天与案件分析页面。
- 由模型自主选择并组合调用的领域工具。
- 支付、账本、对账案件和审计的合成结构化数据。
- 对账规则与操作手册的 RAG 检索和来源引用。
- 证据充分性检查；证据不足时拒绝给出确定结论。
- 解决案件前的 LangGraph interrupt，以及人工确认后的恢复执行。
- 对工具选择、参数、检索、引用、拒答和人工确认的自动化评测。
- Docker Compose、本地使用手册、迁移说明和 GitHub Actions。

### 3.2 明确不做

- 不修改或读取 Java 账本平台仓库和数据库。
- 不连接真实支付渠道，不处理真实资金或个人数据。
- 不实现多 Agent、语音、联网搜索、模型微调或自动写账。
- 不实现多租户、计费、企业级权限系统或生产级高可用部署。
- 不允许模型绕过人工确认解决案件。

## 4. 系统结构

系统由三个可独立理解的部分组成：

1. `web`：基于 Agent Chat UI 的 Next.js 前端，负责对话、案件入口、证据卡片、工具轨迹和确认交互。
2. `agent`：Python 3.12 + LangGraph 服务，负责状态机、模型调用、工具编排、RAG、确认中断和结构化输出。
3. `postgres`：PostgreSQL 17 + pgvector，保存合成业务数据、规则片段、向量、会话检查点和 Agent 运行记录。

服务只通过稳定接口交互。前端不持有模型密钥；模型密钥只存在于 Agent 服务端环境变量。Agent 通过 repository 和 tool 接口访问自己的数据库，不允许生成或执行任意 SQL。

## 5. 合成领域模型

第一版只保留 Agent 分析需要的数据：

- `reconciliation_case`：案件编号、渠道、结果类型、状态、规则版本、金额和时间。
- `payment`：支付编号、渠道交易号、金额、状态和发生时间。
- `ledger_entry`：业务引用、账户、借贷方向、金额和记账时间。
- `audit_event`：操作人、动作、结果、业务对象和时间。
- `rule_document`：规则名称、渠道、版本、生效时间、来源和正文。
- `case_resolution`：处理方式、备注、确认人、确认时间和 Agent run id。
- `agent_run`：问题、工具调用摘要、引用、结论、状态和错误信息。

数据由固定 seed 脚本生成。每次初始化产生相同的演示案件，便于测试、演示和迁移。

## 6. Agent 工具

Agent 只能调用以下白名单工具：

- `get_reconciliation_case(case_id)`：查询案件和当前状态。
- `find_payment_evidence(case_id)`：查询可能关联的内部支付。
- `find_ledger_evidence(case_id)`：查询相关的不可变账本分录。
- `get_audit_timeline(case_id)`：查询案件相关操作时间线。
- `search_reconciliation_rules(channel, rule_version, query)`：按渠道和锁定版本检索规则片段。
- `resolve_case(case_id, resolution_code, note, confirmation_token)`：在确认令牌有效时解决案件。

工具使用 Pydantic 定义参数和结果，执行确定性校验。金额、编号、状态和时间只来自结构化工具结果，不允许从向量检索结果推断。

## 7. RAG 设计

RAG 只处理对账规则和操作手册，不存储实时交易事实。

导入流程按 Markdown 标题和语义段落切分文档，为每个片段保存 `channel`、`rule_version`、`effective_at`、`source` 和 `section` 元数据。中文嵌入固定使用 `BAAI/bge-small-zh-v1.5`，通过 sentence-transformers 在本地生成，模型在容器构建阶段下载并缓存。向量保存在 pgvector 中，避免因切换对话模型而重建知识库。

检索时必须先按案件的渠道和锁定规则版本过滤，再执行向量相似度检索。最终回答引用规则名称、版本、章节和片段标识。没有命中正确版本、引用与结论矛盾或证据不足时，Agent 返回“无法确定”以及缺失证据，不得补写不存在的依据。

## 8. 工作流

LangGraph 使用显式节点而不是把全部逻辑放进一个 Prompt：

1. `parse_request`：识别案件编号和用户意图。
2. `collect_case_facts`：运行受限 ReAct 循环，由模型在案件、支付、账本和审计只读工具中自主选择下一步；最多调用 8 次，达到证据要求或预算后退出。
3. `retrieve_rules`：检索案件锁定版本的规则。
4. `validate_evidence`：检查事实、规则引用和冲突。
5. `draft_analysis`：生成结构化原因、置信说明、证据和建议。
6. `request_confirmation`：涉及解决案件时中断并展示拟执行参数。
7. `execute_resolution`：验证一次性确认令牌后执行解决工具。
8. `finalize`：保存运行结果并生成最终回复。

查询类请求在 `draft_analysis` 后结束。解决类请求必须经过 `request_confirmation`；拒绝确认或确认超时不会修改案件。

## 9. 模型接入

模型层使用服务端配置的 OpenAI 兼容接口，至少支持以下环境变量：

- `MODEL_BASE_URL`
- `MODEL_API_KEY`
- `MODEL_NAME`
- `MODEL_TIMEOUT_SECONDS`
- `MODEL_MAX_OUTPUT_TOKENS`

业务代码不依赖具体模型名称。自动化测试使用可编程假模型，不消耗外部 API；真实模型只用于手工验收和 opt-in 评测。任何密钥都不得进入 Git、日志、前端或测试快照。

## 10. 人工确认与安全

人工确认不是一句自然语言“好的”，而是服务端创建的一次性确认令牌。令牌绑定 `run_id`、`case_id`、`resolution_code`、`note` 和过期时间，有效期为 10 分钟；参数变化后原令牌立即失效。案件已解决、确认过期或令牌重复使用时，执行工具拒绝操作。

`resolve_case` 只修改 Agent 自己的合成案件与处理记录。余额、支付和账本表没有写工具。所有成功、拒绝和失败的解决尝试都记录到 `agent_run` 和审计时间线。

## 11. 错误处理

- 输入缺少案件编号：要求用户补充，不猜测编号。
- 案件不存在：返回明确未找到结果，不调用后续工具。
- 模型超时或限流：最多重试 2 次，分别等待 1 秒和 2 秒；仍失败则保留可重试运行状态。
- 数据库或向量检索不可用：停止分析并说明依赖不可用，不生成结论。
- 工具参数校验失败：把结构化错误返回工作流，模型不能直接绕过校验。
- 规则版本缺失：返回无法确定并列出缺失版本。
- 解决操作并发冲突：读取最新状态并拒绝重复解决。

错误信息不得包含密钥、数据库连接串或完整模型请求内容。

## 12. 测试与评测

后端使用 pytest，前端使用组件测试和少量 Playwright 关键流程测试。至少覆盖：

- 每个工具的正常、未找到和非法参数场景。
- RAG 的版本过滤、来源引用和无结果场景。
- Agent 对不同案件选择正确工具和参数。
- 证据不足时拒答。
- 人工确认前不产生写入。
- 确认令牌绑定、防重放、过期和参数篡改。
- 模型超时、工具失败和数据库失败。
- 从提问到确认解决的端到端演示流程。

固定评测集包含 20 至 30 个合成案例，记录工具选择准确性、参数准确性、规则 Recall@K、引用完整性、结论一致性和拒答正确性。评测结果保存为可比较的 JSON，不使用没有依据的“准确率提升”描述。

## 13. 运行与迁移

Docker Compose 启动 `web`、`agent` 和 `postgres`。首次启动执行迁移、导入规则并写入固定 seed 数据。仓库提供 `.env.example`、健康检查、启动命令、测试命令和迁移手册。

项目迁移到另一台电脑时，只需要 Git、Docker Compose 和个人模型 API Key。数据库可从 seed 重建；不要求复制当前电脑上的数据库或任何公司凭据。

## 14. 验收标准

项目完成时必须满足：

- 全新克隆后可按 README 启动。
- 不启动或修改 Java 账本平台也能完成全部演示。
- 用户可选择一个合成案件并获得带业务证据和版本化规则引用的分析。
- UI 可展示关键工具调用和引用来源。
- 证据缺失案例不会得到确定结论。
- 解决案件前工作流确实中断，拒绝确认不写数据，确认后只解决指定案件一次。
- 自动化测试、固定评测和 GitHub Actions 通过。
- README 明确上游来源、个人实现范围、限制和演示步骤。
